# Version and Release Design

## Goal

Give every distributed aulycmail build a unique, auditable identity while
keeping local test installation fast. The identity consists of:

- a SemVer application version;
- an independently increasing macOS build number;
- the exact Git commit;
- an immutable Git tag for public releases;
- a checksum-bearing manifest beside each release DMG.

## Source of truth

`version.json` is the only file edited directly when changing a version or
allocating a public build number. `tools/version-bump.mjs` synchronizes and
verifies the derived values in `wails.json`, `frontend/package.json`, and
`frontend/package-lock.json`.

The canonical version accepts stable SemVer, `-dev`, and numbered
`-alpha.N`, `-beta.N`, or `-rc.N` prereleases. Build metadata is added only to
local runtime versions and is not stored in `version.json`.

## Runtime and platform mapping

| Consumer | Value |
|---|---|
| About page / `--version` / IMAP client ID | full runtime version and build metadata |
| `CFBundleShortVersionString` | numeric `MAJOR.MINOR.PATCH` base |
| `CFBundleVersion` | independent integer build number |
| Wails `productVersion` | numeric base |
| npm package metadata | canonical full version |

Local builds append the short commit SHA as SemVer build metadata. Test and
formal release builds use the exact canonical version from the release tag.

Release preparation is channel-aware. The test channel advances `beta.N` (or
an existing `rc.N`) and uses explicit ad-hoc signatures. The formal channel
promotes the current development/prerelease base to stable and uses Developer
ID plus notarization. Both channels require committed functional changes and
create their release metadata commit automatically.

## Release gates

A test or formal release must have a non-`dev` version, a positive build number, a
matching changelog entry, a clean worktree, and an annotated no-`v` tag equal
to the version and pointing at `HEAD`. The normal test installation path does
not allocate a build number or require a tag.

The formal DMG is Developer ID signed, notarized, stapled, and verified. A test
DMG is ad-hoc signed and explicitly bypasses only the Gatekeeper assertion that
cannot apply to ad-hoc identities. The manifest records version, build number,
tag, commit, architecture, signature type, notarization submission ID when
applicable, build timestamp, and SHA-256.

## Security and failure behavior

Version input is parsed strictly and release checks fail closed. Signing
identities and notarization profile names are passed through environment or
Make variables; credentials remain in Keychain and are never written to the
manifest or command output generated by this repository.
